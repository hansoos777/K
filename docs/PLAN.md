## 1. 현재 프로젝트 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어·UI | TypeScript + React 19 | PujaTime과 같은 스택이라 Mandir 모듈을 거의 그대로 옮길 수 있음 |
| 빌드 | Vite 7 | PujaTime과 같음, 공간(월드)별 코드 분할이 기본으로 됨 |
| 라우팅 | 해시 라우터 직접 구현(30줄) | 라이브러리 0개, 정적 호스팅에서 서버 설정 없이 동작 |
| 상태·저장 | `useSyncExternalStore` + localStorage (`oruvia-v1`) | 서버 없이 1단계 완성, 2단계에 같은 모양으로 서버 동기화 |
| 다국어 | `src/i18n/ko.ts`(기본 번들) + `en.ts`(고를 때만 다운로드) | 화면 문구 하드코딩 없음 |
| 소리 | Web Audio 합성(종·범종·간타·목탁·죽비·오르간·패드·바람) | 음원 파일 0개 → 저작권·용량·CDN 비용 0 |
| 그림 | 인라인 SVG 장면 | 공간 1개당 수 KB, 저사양 폰에서도 가벼움 |
| 호스팅(예정) | Cloudflare Pages (PujaTime과 같은 계정·wrangler) | 정적 요청·대역폭 무료 |

외부 의존성은 `react`, `react-dom` 두 개뿐이다.

## 5. 추천 아키텍처: 모듈형 모놀리스

```
src/
  core/         공통: store(저장), router, audio, perf(측정), registry(공간 등록부)
  i18n/         공통 문구 ko(기본) / en(지연 로딩)
  ui/           공통 UI: Home, Settings, WorldShell(지연 로딩·오류 처리), kit(WorldFrame·Panel…)
  worlds/
    christian/  meta.ts(장소 이름, 홈에서 씀) · World.tsx · scenes.tsx · strings.ts
    catholic/   + calendar.ts(전례력 계산)
    mandir/     PujaTime 브리지 → 2단계에 PujaTime 소스
    temple/
```

- 새 공간 추가 = `worlds/<id>/` 폴더 + `registry.tsx`에 한 줄. 코어는 월드 안쪽을 모른다.
- 각 월드는 `React.lazy`로 **들어갈 때만** 다운로드되고, 나가면 소리 노드를 정리하고 오디오 장치를 쉬게 한다.
- 서버가 필요해질 때(2단계)도 **하나의 Cloudflare Worker** 안에서 `/api/auth`, `/api/sync` 경로로 나눌 뿐 마이크로서비스로 쪼개지 않는다.

## 6. 추천 기술과 이유

| 필요 | 추천 | 대안과 비교 |
|---|---|---|
| 정적 호스팅·CDN | **Cloudflare Pages** | 정적 요청·대역폭 무료, PujaTime이 이미 사용 중 |
| 대용량 미디어(3D·녹음) | **Cloudflare R2** + 사용자 도메인 캐시 | 인터넷 전송(egress) 무료. S3+CloudFront는 전송량 과금 |
| API | **Cloudflare Workers** (필요할 때만) | 상시 서버 없음, 요청당 과금 |
| DB | **Cloudflare D1** (SQLite) | 사용자 설정·즐겨찾기·기도 노트 동기화에 충분. 관계형 요구가 커지면 Postgres(Supabase 등)로 이전 가능하게 SQL 표준만 사용 |
| 로그인 | Google·Kakao·Apple OAuth를 Worker에서 직접 처리 | 외부 인증 서비스 비용·종속 없음. 개발 부담이 크면 Supabase Auth(무료 5만 MAU)를 검토 |
| 3D(3단계 이후) | **three.js** (해당 월드 청크에만 포함) + glTF·meshopt·KTX2 | 게임 엔진(Unity WebGL 등)은 초기 다운로드 수십 MB → 부적합 |
| 실시간 공동 방문(5단계) | Durable Objects, 방(room) 단위 | 필요한 공간에만, 인원·전송 빈도 제한 |

## 7. 비용 구조와 세 가지 대안

### 확인한 가격 (2026-11 기준, 공식 가격표)

- **R2**: 저장 $0.015/GB-월, 쓰기(Class A) $4.50/백만, 읽기(Class B) $0.36/백만. 무료: 10GB-월, Class A 100만, Class B 1,000만/월. **인터넷 전송 무료**.
- **Workers Paid**: 월 $5 최소. 요청 1,000만/월 포함(초과 $0.30/백만), CPU 3,000만 ms 포함 (요청·CPU 포함량은 제3자 계산기 기준, 공식 페이지에서 다시 확인 필요).
- **D1**: 무료는 하루 읽기 500만 행·쓰기 10만 행·5GB. 유료는 월 읽기 250억 행·쓰기 5,000만 행·5GB 포함, 초과 쓰기 $1/백만 행, 저장 $0.75/GB-월. 전송 무료.
- **Supabase**(대안): 무료 5만 MAU, Pro $25/월부터 10만 MAU 포함.
- **Pages 정적 파일**: 요청·대역폭 무료.

### 가정

- MAU 1명이 한 달에 8번 방문, 평균 2개 공간 입장
- 1단계: 첫 화면 81KB(gzip), 공간당 3~10KB → 사실상 0원
- 3D 도입 후: 공간당 3~8MB(모바일 기준 예산), 브라우저 캐시 후 재다운로드 없음, R2 앞에 Cloudflare 캐시를 둬 Class B 호출 대부분을 캐시가 받음
- 2단계 API: MAU당 월 약 100회 요청, 쓰기 약 20행

### 월 예상 비용 (도메인 비용 제외, 단위 USD)

| MAU | A. 최소 비용형 | B. 균형형 | C. 확장형 |
|---|---|---|---|
| 구성 | Pages + localStorage, 미디어는 R2 | A + Workers Paid + D1 + 직접 OAuth | B + 실시간 방(Durable Objects) + 오류 모니터링 |
| 100 | **$0** | **$5** (최소 요금) | $5 + α |
| 1,000 | **$0** | **$5** | $5 + α |
| 10,000 | **$0** (R2 무료 범위) | **$5** (요청 100만 ≪ 포함 1,000만) | $5~ + 실시간 사용량 |
| 100,000 | $0 ~ 수 달러 (R2 캐시 미스가 많을 때 Class B 초과) | **약 $5~10** (요청 ~1,000만, 쓰기 ~200만 행 → 포함량 근처) | **산정 불가**: 실시간 접속 시간·메시지 수에 따라 크게 변함 → 실측 후 산정 |
| 한계 | 기기 간 동기화·로그인 없음 | 공동 예배·실시간 기능 없음 | 운영 복잡도 증가 |

추천: **지금은 A, 로그인이 필요해지면 B**. C는 공동 방문 수요가 실제로 확인될 때만 공간 단위로 붙인다.

### 비용 급증 방지

- Cloudflare 계정에 사용량 알림, R2·Workers에 월 예산 알림 설정
- Worker에 IP·사용자별 요청 제한, 재시도 최대 2회·타임아웃 5초
- 실시간 방: 방당 인원 상한, 위치 업데이트 초당 최대 2회, 비활성 60초 후 연결 끊기
- AI 기능을 넣더라도 미리 작성한 안내문을 우선 사용, 결과 캐시, 사용자별 일일 한도

## 9. 데이터·리소스 용량 관리

- **공간별 독립 로딩**: 이미 구현됨(빌드 결과 `World-*.js`가 공간마다 따로 있음, 테스트에서 들어갈 때만 다운로드되는 것을 확인).
- **3D 예산(모바일)**: 공간당 다운로드 5MB 이하, 삼각형 10만 개 이하, 텍스처 최대 1024px(KTX2), 그림자는 구워서(baked) 사용, 실시간 조명 1~2개, 공통 오브젝트(촛불·의자·등)는 인스턴싱.
- **이미지**: AVIF/WebP, 썸네일·원본 분리, `srcset`.
- **오디오 녹음**(허가 확인된 것만): Opus 64~96kbps, 들을 때만 다운로드, R2 + 장기 캐시.
- **캐시 정책**: `public/_headers`. 해시 붙은 빌드 파일은 1년 immutable, `index.html`은 no-cache. 사용자 데이터는 캐시하지 않음.
- **DB**: 미디어 파일은 DB에 넣지 않고 R2 경로만 저장.
- **측정**: `npm run size`로 빌드마다 전송량 확인, 설정 > 진단에서 TTFB·FCP·LCP·공간 로딩 시간 확인(외부 분석 서비스 없음).

| PujaTime 소스가 PC에만 있고 git 기록 없음 | **가장 먼저 PujaTime을 git에 커밋하고 GitHub에 백업** (서명 키·keystore.properties는 제외) |
| 종교적 부정확성 | 지금 문구는 일반적 사실 수준. 각 공간 공개 전에 해당 종교인의 검토. 사찰·교단마다 다른 부분은 화면에 "다를 수 있음"으로 표시 |
| 경전·기도문·찬송 저작권 | 한국어 성경·기도문 본문은 넣지 않음(구절 위치와 직접 쓴 묵상 질문만). 음악은 공개 저작물(1551년 선율) 또는 직접 합성 |
| 고해성사 오해 | 교육 공간으로만 구현, 입력 칸 없음, 성사는 본당에서 받도록 안내 |
| 3D 도입 시 용량·발열 | 9절 예산, 저사양 자동 감지, 2D 장면을 대체 화면으로 유지 |
| 실시간 기능 비용 폭증 | 실측 전에는 도입하지 않음, 도입 시 방 단위·인원 상한 |
| 외부 서비스 종속 | 표준 SQL, 미디어는 S3 호환 R2(다른 곳으로 옮기기 쉬움), 사용자 데이터 JSON 내보내기 기능 제공 |
| localStorage 유실(브라우저 정리) | 설정에서 JSON 내보내기, 2단계에서 계정 동기화 |

## 사용자 결정이 필요한 것

1. PujaTime 소스를 이 저장소로 가져올지(또는 PujaTime용 저장소를 따로 만들지)
2. 도메인(예: oruvia.com 등) 구입 여부, Cloudflare Pages 프로젝트 이름
3. 로그인 방식(Google·Kakao·Apple 중 무엇을 먼저)
4. 종교별 콘텐츠 검토자
